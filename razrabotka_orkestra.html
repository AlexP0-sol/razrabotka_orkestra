    Сравнение вариантов:

    1. Китайский язык (中文):

      • Плюсы: Китайский язык невероятно информационно плотен. Один иероглиф — это целое слово или концепт. В токенизаторах моделей семейства GLM (где используется кастомный двуязычный токенизатор на базе Tiktoken) большинство базовых иероглифов занимают ровно 1 токен. Фраза, которая на русском займет 15 токенов, на китайском может занять всего 4–5 токенов.
      • Минусы (КРИТИЧЕСКИЕ):
        • Кодовая база, имена библиотек, переменные, стек-трейсы ошибок компилятора (SyntaxError, null, kwargs, asyncio) написаны на латинице (ASCII).
        • Когда модель постоянно переключается между китайскими иероглифами и английским кодом, токенизатор «ломается» на границах байтов (Byte-Pair Encoding boundary splitting), что иногда увеличивает расход токенов и приводит к микро-сбоям синтаксиса в коде.

    2. Русский язык:

      • Для межагентного общения категорически не подходит. Кириллическое слово средней длины занимает от 2 до 4 токенов (в 3 раза «дороже» английского и китайского). Тратить токены на русский язык внутри закрытого роя — расточительство.

    3. Технический Телеграфный Английский (Technical Telegraphic English / Code-English) внутри JSON-RPC:

      • ЭТО АБСОЛЮТНЫЙ ПОБЕДИТЕЛЬ.
      • Почему:
        1. Модели GLM и Nemotron обучались на гигантских массивах GitHub, где 99% документации, тестов и кода — на английском. Семантические веса кода в весах нейросети намертво привязаны к англоязычным терминам.
        2. Имена ключей в JSON, типы данных (int, str, List), названия функций — все на английском. Нулевой оверхед на смену кодировок.
        3. Телеграфный стиль (Telegraphic Style): Агенты системно лишаются предлогов, артиклей (a, the) и вспомогательных глаголов.

class AgentOutput(BaseModel):
    agent_id: str
    role: str
    full_reasoning: str  # Все мысли агента (для аудита и WebUI)
    final_content: str  # Итоговый код или JSON-контракт


class AsyncNvidiaAgent:

    def __init__(
        self,
        agent_id: str,
        role: str,
        api_key: str,
        model: str = "nvidia/nemotron-3.5-lightning-30b-a3b",
        reasoning_budget: int = 16384,
        temperature: float = 0.0,
    ):
        self.agent_id = agent_id
        self.role = role
        self.client = AsyncOpenAI(
            base_url="https://integrate.api.nvidia.com/v1", api_key=api_key
        )
        self.model = model
        self.reasoning_budget = reasoning_budget
        self.temperature = temperature

    async def execute_task(
        self,
        system_prompt: str,
        task_prompt: str,
        on_reasoning_chunk: Optional[callable] = None,
        on_content_chunk: Optional[callable] = None,
    ) -> AgentOutput:
        """Асинхронно исполняет задачу с параллельным стримингом мыслей и контента."""
        messages = [
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": task_prompt},
        ]

        # Конфигурация мышления и детерминизма
        extra_body = {
            "chat_template_kwargs": {"enable_thinking": True},
            "reasoning_budget": self.reasoning_budget,
        }

        reasoning_accumulator = []
        content_accumulator = []

        try:
            stream = await self.client.chat.completions.create(
                model=self.model,
                messages=messages,
                temperature=self.temperature,
                max_tokens=16384,
                extra_body=extra_body,
                stream=True,
            )

            async for chunk in stream:
                if not chunk.choices:
                    continue

                delta = chunk.choices[0].delta

                # 1. Обработка потока мыслей (Reasoning Stream)
                reasoning = getattr(delta, "reasoning_content", None)
                if reasoning:
                    reasoning_accumulator.append(reasoning)
                    if on_reasoning_chunk:
                        # Отправка мысли в WebUI или логгер
                        await on_reasoning_chunk(self.agent_id, reasoning)

                # 2. Обработка полезного кода / ответа (Content Stream)
                if delta.content is not None:
                    content_accumulator.append(delta.content)
                    if on_content_chunk:
                        # Отправка кусочка кода в UI
                        await on_content_chunk(self.agent_id, delta.content)

        except Exception as e:
            # Логирование ошибки конкретного ключа/агента
            print(f"❌ Ошибка агента [{self.agent_id}]: {e}")
            raise e

        return AgentOutput(
            agent_id=self.agent_id,
            role=self.role,
            full_reasoning="".join(reasoning_accumulator),
            final_content="".join(content_accumulator),
        )

    1. Как устроена мультиагентность в Claude Code?

    Многие думают, что Claude Code — это толпа спорящих агентов. На самом деле — нет.

    Архитектура Claude Code (как и SWE-agent от Принстона) устроена по принципу Single-Agent + Sub-routines (Один главный агент + специализированные подпрограммы):

    1. Главный агент (Orchestrator Loop): Он работает в цикле Think -> Act -> Observe.
    2. Как реализованы «агенты» внутри него: Когда Claude Code сталкивается с задачей поиска по репозиторию, он не тратит основной контекст. Он запускает Sub-agent (под-агента) с урезанным контекстом, единственная задача которого — вызвать grep или find, проанализировать 50 файлов, вытащить 10 нужных строк и вернуть главному агенту только чистую выжимку.
    3. Сила Claude Code не в рое, а в инструментах (Tools):
      • Он правит файлы не переписыванием всего кода, а через Patching (замену конкретных кусков по строкам).
      • У него есть доступ к реальному Bash-терминалу.

    1. Архитектура динамического пула ключей (Key Management Pool)

    В системе создается компонент Key Manager:

    • В конфигурации лежит список ваших API-ключей: [KEY_001, KEY_002, KEY_003 ... KEY_N].

    • Агент завершил работу? Ключ возвращается в пул и может быть переиспользован для следующего этапа (например, этапа тестирования).

    2. Как Архитектор формирует команду (Dynamic Team Composition)

    Когда вы присылаете ТЗ (и после того, как Архитектор уточнил у вас все детали в Telegram), он выполняет шаг «Organizational Design» (Проектирование команды).

    2. Количество ролей: Ровно столько, сколько требует логика декомпозиции (от 2 до 10+).
    3. Назначение обязанностей: Никаких расплывчатых рамок.
